# Internals

This is the detailed reference for ibara's core: each module, the programs it calls, its failure codes and the choices behind them. Start with [architecture](architecture.md) for the overview and [development](development.md) for building and testing.

The core is one crate that builds 2 programs:

| Binary | Runs | What it is |
|---|---|---|
| `ibarad` | One per computer, long-lived | The service behind agents and consoles: the controller, its sockets, pairing, the display watcher and, with `--role operator`, the console's service |
| `ibara` | Short-lived commands | `ibara mcp` and the other commands a person or agent runs, the agent entry (`ibara agent-entry`), the root helpers and the Chrome native messaging host (`ibara chrome-host`) |

ibara was first written in TypeScript for Node, then ported to Rust before its first public release. That earlier version was never published. This reference still names what each module replaced, and lists where the Rust deliberately behaves differently, because those notes explain behavior a newcomer might otherwise take for a mistake. Where a doc comment cites a section (§) of a map of the old system, the map itself is not published either.

## Rules

- **No Node and no Python at run time.** On the desktop, shell out only to these programs: `hyprctl`, `grim`, `cua-driver` (a private MCP child for input and accessibility), `omarchy-toggle-idle` (keeping the computer awake while an agent holds it), `ibara-stream` (the stream Take Control opens, a child of `ibarad`), `wl-paste`/`wl-copy` for the clipboard shared during Take Control, and `wf-recorder` for Live Video (Preview). Everything else ibara runs is a system tool such as `tailscale`, `ssh-keygen`, `setfacl`, `journalctl` or `ip`.
- **Memory is a pass/fail requirement.** `ibarad` must stay at or below 40 MiB idle (proportional set size plus swap).
  - Use one current-thread Tokio runtime.
  - Keep no unbounded caches.
  - Stream large bodies instead of buffering them.
  - Drop image buffers as soon as they are encoded.
- **One contract.** The tool definitions, their JSON Schemas, the error registry and the CLI help all come from the types in `src/contract/`. Do not hand-write a schema elsewhere.
- **Persist intent before effect.** Every effect is written to the store as `running` before it is dispatched. After a restart, anything still `running` becomes `unknown`.
- **Tests:**
  - End-to-end first, through `ibara` against a real `ibarad`.
  - Isolated tests only for logic with clear failure cases (fingerprints, migration, schema generation). Write the failure cases first.
  - No tests that mirror the implementation.

[Security and access](security-and-access.md) describes the authoritative records, exact approval boundary, generated transport and migration/recovery. `access.rs`, `controller/access.rs` and `access_system.rs` own those parts; legacy files become transport projections.

## Contract and MCP

`src/contract/` holds contract 4 ([agent tools](agent-tools.md)); `src/mcp.rs` serves it over stdio.

| Module | Holds |
|---|---|
| `contract/tools.rs` | The input type of each of the eleven tools, and the `Action`, `Expectation`, `Check`, `BrowserAction` and `FilesOp` unions |
| `contract/envelope.rs` | `Envelope {situation, status, since, result, error}` and the result types (`BeginResult`, `Frame`, `ActResult`, `FinishResult`, `FilesResult`, `WaitResult`, `StatusResult`) |
| `contract/schema.rs` | `tool_definitions()` and `help(tool)`: the summary, long description and example of every tool, with schemas generated from the input types |
| `contract/render.rs` | `render_text(&Envelope)`, the compact text that MCP sends as `content[0]` |
| `contract/mod.rs` | `Ref`, `parse_input`, the `Validate` trait and the `tagged_union!` macro |
| `mcp.rs` | `serve(reader, writer, handler, ping, heard)`: newline-delimited JSON-RPC with `initialize`, `ping`, `tools/list` and `tools/call`. It also sends the client a `ping` every `ping` interval and sets `heard` whenever the client sends anything. The handler receives `(name, arguments, ClientInfo)`; `ClientInfo.name` from `initialize` is the agent name |

**Parsing.** Always parse arguments with `parse_input::<T>(tool, &args)`. It refuses unknown fields, and its `INVALID_ARGUMENT` message starts with the exact field path, for example `steps[2].expect.kind: unknown variant 'windw', expected one of window, …`. Unions tagged by `kind` or `op` are declared with `tagged_union!`, never with `#[serde(tag)]`, because serde's tagged enums lose the path of any error inside them. Rules that serde cannot express, such as "exactly one of" or duplicate ids, go in the type's `Validate` impl.

**Schemas.** Schemas are generated, then compacted: optional fields drop `null`, titles and defaults go, unions become one object whose `description` lists each kind's fields, and a large subschema that repeats is replaced by a pointer to its first appearance. The whole `tools/list` must stay at or below 10 KiB (9.1 KiB with the read-only hints in 0.1.0-18); a test checks this.

**Adding or changing a tool:**

1. Add or change the input struct in `contract/tools.rs`. Use `#[serde(deny_unknown_fields)]`, `Ref` for ids and references, `at_most::<_, _, N>` for bounded lists, and give each struct a `Validate` impl (it can be empty).
2. Add or change its entry in `TOOLS` in `contract/schema.rs`: a summary of one or two sentences saying when to use the tool and what it really does, the long description, and one example. A test parses every example.
3. Add any result type to `contract/envelope.rs`. If its shape is new, teach `render.rs` a short rendering of it.
4. Update `docs/agent-tools.md`, then run `cargo test` to check the size budget and schema validity.

## Desktop layer

`src/desktop/` holds every effect on, and observation of, the local Hyprland desktop, as primitives the controller composes. Doc comments cite sections (§) of a map of the retired Node system, which is not published. Build a `Desktop` with `Desktop::new(DesktopConfig::from_env())` (no I/O) and share it in an `Arc`. `IBARA_TEST_PREVIEW_TOOLS=1` swaps in `IBARA_TEST_HYPRCTL`, `IBARA_TEST_GRIM`, `IBARA_TEST_CUA`, `IBARA_TEST_IDLE` and `IBARA_TEST_WF_RECORDER`.

**Every helper goes through `run::run`** (§2):

- It runs argv only, never a shell, with a combined output cap (32 MiB by default).
- On timeout or `Cancel`, it sends SIGTERM, then SIGKILL after 300 ms. If the helper has not closed 1800 ms after cancelling began, the call fails with `CONTROL_UNSETTLED`.
- A cancelled mutating helper is `OUTCOME_UNKNOWN`. A cancelled read is a retry-safe `TIMEOUT`.
- A missing program is `CAPABILITY_UNAVAILABLE` with `execution_not_started`.
- Each child is supervised by its own task. Dropping the caller's future never stops a helper: only the timeout or an explicit `Cancel` does.
- Mutating helpers count as in flight until they close. `run::wait_for_helpers` is the 2.5 s barrier before held input is released.

**Effects are wrapped.** Every effect primitive (`launch` to `type_text` below) is wrapped the same way as today's `act`. None starts once its `Cancel` has fired (control changed hands). On any error it waits for helpers and releases held input; if that fails the error becomes `CONTROL_UNSETTLED`. It also adds `execution_not_started` when no mutating helper ran.

**One cursor on the screen at every moment (`desktop/handover.rs`).** Hyprland's pointer is the person's; the agent's named cursor is Cua's. The rule: the person's pointer stays hidden for the whole time an agent holds control, and comes back only when a person takes over. The screen is handed over, never shared, in this one place:

- **To the agent** when control begins (`Desktop::set_agent`, from `begin`), not at its first input, and at the agent's next input after a person took the screen: the named cursor is drawn exactly where the pointer is, then the pointer is hidden, so for a moment both are drawn in one place, never neither. It stays so however long the agent works or thinks, with no hand-back between inputs: Cua's idle hide is off, the worker is not stopped for idleness while the named cursor is drawn, and when the worker exits anyway (a crash) the watch sees it within 20 ms, shows the pointer at once and draws the named cursor again on it. If the person moves the mouse during a take, the named cursor goes again and the screen stays theirs. If the named cursor or the pointer cannot be handed over, the input is refused, nothing sent (`CAPABILITY_UNAVAILABLE`, `reason: agent_cursor_unavailable`); a take that failed at the start of control is tried again every second.
  - Each take is a new Cua session under the agent's label: a hidden cursor drawn again shows at its old place for 50–80 ms first, while a new session's first cursor, placed with a seed move 151 px down and right of the point, is drawn only at the point, 31–36 ms after the move (probed on Cua 0.29.1). The session's glides land in one frame (`glide_duration_ms: 1`; `0` means a speed-based glide), turn little (`turn_radius: 1`; the default swung a short glide 46 px past its point, off the screen's edge), and never hide for idleness (`idle_hide_ms: 0`; Cua caps other values at 60 s). A point click's glide is still paced to a person's pointing time. Every `set_agent_cursor_motion` call sets all three: Cua 0.29.1 on Wayland fills each field a call leaves out with its own default, not the session's current value, so a point click's glide set alone brought back turns of 80 px, which swung the cursor past the screen's left edge on its way to a button (neither cursor on the screen for 267 ms), and a hide after 20 s idle.
  - The named cursor stays where a screen shows it. A lead to an element no screen shows (scrolled out of sight) stops at the nearest point one does; a point click, or a drag's start or end, at a point no screen shows is refused (`INVALID_ARGUMENT`); and from one screen to another the cursor lands in one frame, since the straight way between two screens may cross what neither shows.
  - Typing and keys move only the named cursor, and only for typing. Before a `computer_act` type's first piece, ibara reads the window (walking its tree for up to 1 s) and, when a whole read shows exactly one enabled editable text element whose box Cua gives wholly inside the window, the named cursor glides to that box's middle at a person's pace (as a lead does) unless it is in the box already; otherwise it stays. Cua 0.29.1 on Hyprland gives a GTK 3 window's text boxes in the window's own coordinates (Mousepad's text at 1,30 in a window at 12,38), which lie outside the window unless it is near the screen's corner, so those are not followed. A browser window is not read: `browser_act` typing follows its click on the field, which already put the named cursor there, and an untargeted page type leaves it where it is. Keys never move it. Every key and typing piece carries the agent's session, so Cua's overlay plays its `text` and `key` animations with the `foreground` delivery chip under the cursor (the Linux driver has no other cue and no custom badge text). The cursor moves are Cua's `move_cursor` without `scope: desktop`, which leaves the real pointer alone, and the Hyprland plugin moves the pointer only for point clicks, drags and wheel notches; keys and text only activate the target window, which already has the focus.
  - The pointer is hidden with `cursor:inactive_timeout` 0.1 s, not `cursor:invisible`. Hyprland 0.56 applies either only on its 500 ms cursor timer, so both cursors stay in one place for up to 0.5 s at each take, and the take waits 0.65 s before the agent's input goes (nothing moves either cursor meanwhile). This timeout Hyprland undoes by itself as soon as a person moves the mouse (the pointer is drawn 14–49 ms after the first move), ibara's own pointer moves and focus changes do not draw it, and one `hyprctl eval` that puts back the person's own timeout and moves the pointer draws it within 8–26 ms (all probed on a test computer).
  - A Hyprland config reload (`hyprctl reload`, Omarchy's theme, font and toggle commands, a saved config file) puts the config's timeout back in place of ibara's, and Hyprland would draw the pointer again at its next cursor tick. While an agent holds control, ibara reads `cursor:inactive_timeout` from the request socket every 20 ms along with the pointer's position; when it is no longer 0.1 s, the reloaded value becomes the person's own in the marker and the pointer is hidden again.
- **To the person** when control ends (finish, pause, Take Control, revoke, expiry, disconnect: `gather_cancellation` clears the agent before it releases input; shutdown does the same), or at once when the person moves the mouse. The pointer is shown first and the named cursor hidden after it (Cua takes 30–70 ms) without waiting for Cua's call in flight: a read (`get_window_state` takes up to 12 s) is stopped by stopping the worker, which takes the named cursor with it, and the read is taken again on a new worker. Any input in flight is waited for, and nothing follows it: the plugin refuses a click or drag as soon as the pointer moves, and a typing piece in flight (16 characters, about 430 ms with Cua 0.29.1, which types key by key) ends whole, so the named cursor stays until it does. Stopping Cua's worker in the middle of a piece instead crashed Mousepad (GTK 3, a segfault in `gtk_main_do_event`) in 4 of 26 moves during typing.
  - When control ends, both meet in one place first: the pointer comes back on the named cursor when that is inside the focused window (moving it elsewhere could move the keyboard focus), else the named cursor moves onto the pointer (it lands about 50 ms later). A failed `hyprctl eval` leaves the named cursor and the agent's hold, and the watch tries again every 20 ms.
  - After the person's own move, Hyprland already draws the pointer where they put it; ibara puts the person's timeout back (so it does not hide again) and hides the named cursor at the same time, and tries the show again every 20 ms if it failed.
- **Agent input only while the agent has the screen.** Cua draws a hidden named cursor again when it moves it (Cua 0.29.1), so nothing is sent while the person has the screen: the agent's next input waits until the mouse has been still for 1 s, takes the screen back where the person left the pointer, and is refused after 3 s, nothing sent (`CAPABILITY_UNAVAILABLE`, `reason: person_active`). An input already under way when the person takes the screen sends nothing more to Cua (an element click after its lead, a point click after its wait, the next typing piece) and is refused the same way; a point click does not move the person's pointer onto the named cursor. Cursor calls (`pace`, `lead`) are skipped while the named cursor is hidden. When part of a step already went through, the step never says that nothing was sent: a typing step says how many characters were typed for sure and how many more may have been, and asks the agent to check before typing again; any other step says that part of it went through.
- **Seeing the person.** Cua's plugin refuses an input in flight when the real pointer moves (`reason: interrupted`). While an agent holds control, ibara also reads the pointer's position from Hyprland's request socket (`j/cursorpos`) every 20 ms, and twice, 20 ms apart, before the first take. A change while no agent call could move the pointer (point clicks, drags, wheel notches, ibara's own pointer moves, focus and close) is the person's.
- ibara starting or stopping (`reset_input`) stops Cua, which takes the named cursor with it, and shows the pointer. While ibara has the pointer hidden, a marker, `<state>/pointer-hidden`, keeps the person's own `cursor:inactive_timeout` (`inactive_timeout 0`), so a start after a crash shows the pointer and puts their timeout back. Their timeout goes back only while the live one is still ibara's 0.1 s: after a new Hyprland session (Hyprland exited while an agent held control) or a reload, the live one is the person's current setting and stays; the pointer is only drawn. ibara 0.1.0-5's empty marker (it hid the pointer with `cursor:invisible`) makes the start clear `cursor:invisible` instead. A take settles a marker left over first (a failed show, 0.1.0-5's), so the timeout it keeps is always the person's. A pointer the person hid themselves with `cursor:invisible` stays hidden and is left alone. Hiding and showing the pointer is not counted as input, so `execution_not_started` stays exact; the pointer ibara moves onto the named cursor when it hands the screen back is counted as its own move, not the person's.

A cursor is the encoder's generation (high bits) plus its byte offset (low 32 bits). A read without a cursor, or with one the ring cannot serve, starts at the encoder's first byte (`reset` when it had a cursor), restarting the encoder when that byte is gone; a read without a cursor also restarts an encoder that started more than 1 s before, so a new reader starts live; at most 1 MiB a read. An encoder stops 5 s after its last read, and on `stop_video`; one that ended is not restarted for 5 s (`ended` once read to its end) | `VIDEO_UNSUPPORTED` (no hardware encoder, or `wf-recorder` missing, in plain words), `CAPABILITY_UNAVAILABLE` (`locked`, `no_display`) |
| `capabilities` | the probes of `native.ts:321-348` | none: rows report `unavailable` with a reason |
| `subscribe`, `start_watch` | `$XDG_RUNTIME_DIR/hypr/<instance>/.socket2.sock` | none: reconnects every 3 s; publishes `Resync` and `DisplayChanged` on every connect |
| `chrome::ChromeBridge` (`listen`, `connected`, `call`, `tabs`, `cancel`, `close`) | `<runtime>/chrome.sock` (0600) | `CAPABILITY_UNAVAILABLE` (disconnected, or a read timed out), `BUSY`, `STALE_TARGET` (the extension refused before dispatch), `OUTCOME_UNKNOWN` (an effect not acknowledged; the bridge then stays unsettled), `CONTROL_UNSETTLED` (`cancel`) |

**Cua.** `desktop/cua.rs` runs `cua-driver mcp` as a private child over pipes, with `CUA_DRIVER_RS_ENABLE_WAYLAND=1`. Every `cua-driver` run (Cua 0.28.2 names, checked in its source) also gets `CUA_DRIVER_RS_TELEMETRY_ENABLED=false`, which overrides any saved preference; `CUA_DRIVER_RS_UPDATE_CHECK=false`, because `mcp` otherwise asks GitHub's releases API for a newer version as it starts and the telemetry setting does not cover that; and `CUA_DRIVER_TELEMETRY_HOME` and `CUA_DRIVER_RS_HOME` set to `<state>/cua`, so Cua's installation ID and telemetry markers stay out of the desktop user's shared `~/.cua-driver`. Cua ignores `CUA_DRIVER_HOME` for these; before this was corrected, `cua-driver telemetry disable` wrote `telemetry_enabled: false` into the desktop user's own `~/.cua-driver/config.json`.

- The worker starts on the first call and stops 120 s after the last one (checked every 10 s), but never while the agent's named cursor is drawn: the cursor goes with the worker. Before each start, `cua-driver telemetry status --json` with the same environment must report `enabled: false` from `source: environment`; otherwise the worker does not start.
- Calls are serialised. A call that times out stops the worker: `OUTCOME_UNKNOWN` for an effect, `TIMEOUT` for a read. A route Cua refused before dispatch keeps `execution_not_started`; it is never retried on another route, except an element's left click refused as background input, which the pointer makes instead (element `click` above). A JSON-RPC error is Cua's answer, so the worker stays: a rejection before any tool runs (unknown tool, invalid parameters, protocol version, in-flight limit) is `CAPABILITY_UNAVAILABLE` with Cua's message and `execution_not_started`; any other error code after an effect call is `OUTCOME_UNKNOWN`.
- The task's agent label (`codex@vesper`) is the Cua session, so each agent's cursor is its own, and Cua writes the label beside it. The controller sets it at `begin` and clears it at release. Each handover to the agent opens the session anew with Cua's idle hiding off, and the handover alone shows and hides its cursor; it ends at the next handover, when the agent changes or when the worker stops. Cua picks the cursor's color from a hash of the session name and a random key it makes each time it starts (`cursor-overlay/src/theme.rs`, `namespace_runtime_args` in 0.28.2 and 0.29.1), so the same agent's color changes from run to run and ibara cannot know it. ibara names no color; the label identifies the agent.
- Elements carry an identity (role, label, the ancestors' roles and labels, and the rank among identical siblings), because Cua's indices and tokens change with every snapshot.
- Input needs Cua's Hyprland plugin (`vendor/cua-hyprland-plugin`, built on each computer by `packaging/ops/cua-plugin.sh` from `ibara setup`, and again by the package's pacman hook after Hyprland, GCC or ibara changes; loaded from `/opt/agent-computer/cua` by one line in the user's `hyprland.lua`). ibara's patch accepts Omarchy's keyboard options and NumLock, and lets only a real pointer move interrupt the agent: Hyprland also reports a move, without the pointer moving, when a popup such as GTK's path completion list appears. It lets keys and points reach the target window's own popup while that popup holds the seat grab (a GTK popover or menu), as a person's would; upstream refuses all input during any grab. It also registers a pointer device of its own, `ibara-agent-pointer` in `hyprctl devices`, on every computer: Hyprland gives apps a pointer, and pointer focus, only while some pointer device exists, so without it a computer with no mouse refused every click (`physical_pointer`). The device sends no events, so it never counts as a person; a mouse, a touchpad, Take Control's passthrough pointer or `ydotool` still take over when they move. A rebuild replaces the file on disk only; the running session keeps the module it loaded until the next sign-in, so a computer without a mouse can click only after the sign-in that follows the update (a fresh install loads the plugin at once). Every refusal Cua gives before any input carries a `next` naming what the agent can use instead: keys for a refused pointer, the pointer or `computer_files` for refused typing, and an element's accessibility action while another app's popup, a panel or a drag holds the pointer and keyboard.
- Hazards: another app's menu or popup, a panel with exclusive input (a launcher) or a drag refuses foreground input to the window (`BLOCKED_BY_DIALOG`, `reason: grab` or `dnd`); a left click on an element by its accessibility action still works. The window's own popup does not refuse (see `key` above). Cua reports every foreground refusal before dispatch as `reason: primary_target_busy` with the cause in `detail`, so ibara maps the detail: only a grab or drag and drop is a dialog. Cua's desktop-scope keys and any other virtual keyboard (for example `wtype`) replace the seat keymap, after which Cua refuses keys with `unsupported_layout` until a keyboard with a full keymap types again. ibara never sends desktop-scope keys. Hyprland's `send_shortcut` is not a virtual keyboard: it sends through the seat's own keyboard and keymap.

**Replay pictures.** `controller/replay.rs` keeps a before-and-after crop (at most 640 pixels, 48 KiB, WebP or JPEG) of the window each desktop step acts on, in `<state>/replay/`, and names them in the step's receipt and timeline event. Pictures last 14 days, or 90 for send, spend, destructive and access steps and unknown outcomes, within a cap of 1 GiB or 5 % of the disk. Typing into a window that shows a password field keeps no picture; typed text is never stored. The console's Activity tab shows them.

**Events.** `watch::reconcile_on_display_change(desktop.subscribe(), reconcile)` repeats output-watch's loop in-process. It reconciles at start and after each `DisplayChanged`, and retries every 5 s while `reconcile` returns `true`. Title events are coalesced to one every 500 ms per window, and focus is published only when it moves. A receiver that lags must re-read state.

**Deliberate differences from the TypeScript controller:**

- **Agent images:** these are crops of the requested surface, WebP or JPEG within a byte budget. Today's are full-resolution PNGs of the focused monitor (contract 4). `capture_surface` refuses a window on a hidden workspace instead of returning whatever covers its rectangle.
- **`grim` writes PPM, not PNG:** frames need no decode, and the size is known from the header before anything else is done.
- **Pixel handling:** resampling is an area average, not Lanczos, and palette quantisation is median cut, not libimagequant. Both are bounded by the same byte budgets.
- **`hyprctl eval` errors:** Hyprland 0.56 prints Lua errors on stdout and exits 7, so today's focus path reported a vanished window as `INTERNAL_ERROR`. Focus and close now read the text first and return `STALE_TARGET`.
- **One Hyprland instance:** the operator path used `/usr/bin/hyprctl` without `-i` (hazard 6). Every call now uses `-i 0`, and the event watcher connects to the instance that `hyprctl instances` lists first.
- **Typing in pieces:** text goes in pieces of 16 characters, 40 ms apart; a handoff does not cancel a piece once started (a person's own mouse move does, see the one-cursor rule); cancelling takes effect between pieces. Faster pieces made a GTK file chooser ignore the Return that followed. A piece's 15 s timeout only guards against a hung worker, which is then stopped.
- **Typing through a display change:** Hyprland's Cua plugin ends every input connection when a display is added or removed, and Cua then stops a piece before its next key and says how many keys went out (`text_interrupted`, `delivery.delivered_count`). Exactly those arrived, so typing goes on from there after 500 ms, past the same focus and cancel checks as the next piece, up to 3 times in one text. When the connection fails with a key sent (`transport_or_protocol_error` with a count), only that key is unsure and typing stops. Before this, a display plugged in mid-path stopped a Save As with 16 characters unsure.
- **A pause after typing:** a key or button press that comes within 250 ms of typed text waits out the rest. Apps take typed text in asynchronously: Mousepad's GTK Save As dialog dropped a Return sent about 50 ms after its path was typed. The TypeScript controller never sent a key straight after typing, because each step was its own call.
- **Event watcher:** `output-watch.mjs`'s HTTP and bearer-token hop and its 1 s poll are gone; it is an in-process event.
- **No release-input step:** Cua's plugin releases held keys and buttons when the worker's connection closes, so the unit has no `ExecStopPost` and `ibara release-input` is gone.
- **Hyprland's `FALLBACK` is not an output:** Hyprland lists this placeholder when no real output exists. `output_change` asks for `IbaraVirtual` when `FALLBACK` is all that is listed, so the headless output also returns when the last physical output is unplugged. The TypeScript controller counted `FALLBACK` as physical and never created it (hazard 9).

**Not ported:**

- **Element bounds.** The C helper reports no extents, and its protocol is kept, so elements carry no bounds. There is also no `set_text` operation: click the element, then use `type_text`.
- **Surface, frame, element and observation registries,** pixel-freshness checks, the summary text and successor evidence. These belong to the controller; the layer provides `geometry_key`, `region_hash` and `EncodedImage::to_logical` for them.
- **Preview reply fields.** `frame_sequence`, `endpoint_id` and the authorisation fields are the operator service's.
- **The pre-aborted `CANCELLED` code in `ChromeBridge.call`.** It is not in the error registry, and authority checks are the controller's. The `ChromeBrowser` adapter (tab and element registries, the link-only click policy, capability rows) is also the controller's.
- **Dead code:** `browserWindowBinding`, `InputClient.moveAbsolute`, and `hyprctl layers` and `keyword`. (The pointer's position is read again, from Hyprland's request socket, for the cursor handover.)

**Hazards kept for parity:**

- A Chrome effect that is never acknowledged leaves the bridge unsettled until `ibarad` restarts (hazard 3).
- The host reads `allowed_origins` from `<install root>/browser/native-host.json`, written by `ibara browser-setup` with this computer's extension id.

### Browser pages

`chrome-extension/` (plain files, no build) is the page reader: `document.js` observes, checks text, locates an element (scroll into view, wait until it is at rest, uncovered point, window and viewport sizes) and reports which element the next trusted press reached; `field` says whether the field ibara just clicked has the keyboard focus and, given the text ibara typed, whether the field holds it (line ends compared as `\n`), and never returns the field's value, so a password or a large text never leaves the page; `keys` says whether Return or space pressed now submits a form that posts; `worker.js` adds the tab zoom and opens addresses. It never clicks or types. A checkbox or radio button whose native box is hidden under its label (Bootstrap's `custom-control-input`, Tailwind's `sr-only`) is reached through its own label, which toggles it; a link or other control inside that label does not count. After a scroll, `locate` waits two frames (the page's scroll handlers and lazy loading run on later frames), then takes a point only when, a frame later, the element's centre has not moved and the point still reaches it; an element still moving after 1 s is refused (`STALE_TARGET`). Cua's travel, rest and press are one turn of the plugin, so the point cannot be checked again between the pointer's arrival and the press; the press check below catches a change in that time. `locate` also opens a port from the page to the worker, named after its watch; over it the page reports the press, a form that press submits and the page leaving (`beforeunload`) the moment each happens, and the port closes when the page goes, so a navigation the press starts cannot lose the report. For a plain click `verify` waits up to 150 ms for the page to start leaving (or the tab to have a pending address) and then up to 3 s for it to go, and answers where the tab went: the step reads `click button "Send" · the click reached it; the page then went to <address>`, without the address's query or fragment, which carry what a GET form sent. `controller/agent.rs` maps a page point to the desktop (`page_point`: `x·zoom`, `(outerHeight − innerHeight·zoom) + y·zoom`, refused when the window and page disagree, something sits beside the page, or the band above the page is taller than the browser's bars make it (`BROWSER_BARS_MAX`, 200 px: developer tools docked below the page shorten it, and the page cannot tell they are below)) and clicks with Cua through `Desktop::click`. A click is done only when the page saw the press on the chosen element; a press on another element, a press the page never saw (it landed in the browser's own controls, developer tools or another window) or no answer is `OUTCOME_UNKNOWN`, and a typing or select step goes no further. Select opens the list with a click, types the option's label and presses Return. Type clicks the field and types only once `field` says the page has the keyboard focus and that field holds it (never the address bar); otherwise it is refused with nothing typed. It then selects the field's text and types over it: ASCII with Cua's keyboard, and each run of other characters, which Cua cannot type, as a paste. For that `desktop/selection.rs` sets the person's clipboard aside first (every type it offers, byte for byte, at most 32 MiB), offers the run (marked `x-kde-passwordManagerHint: secret`, so clipboard histories skip it), ibara presses Ctrl+V with Cua and waits up to 2 s for `field` to show the text so far before sending anything else, and afterwards puts the clipboard back unless something else was copied meanwhile. Text beyond ASCII needs a field: without `target`, or typed with `computer_act` into a browser window, where it would reach the address bar, it is refused. `entry/browser_setup.rs` packs a CRX3 (stored zip, RSA proof via `openssl`) and writes the policy. ibara's plugin patch (`vendor/cua-hyprland-plugin/IBARA.md`) makes a click travel at a person's pace; `desktop/cua.rs` paces the named cursor to match (`human_glide`) and `Desktop` hides Hyprland's pointer while an agent holds control.

### The operator directory

`operator.sqlite` stays at schema 2 and is opened in place. Its path is `--directory-db`, then `$IBARA_OPERATOR_DIRECTORY_DB`, then `$XDG_STATE_HOME/ibara/operator.sqlite` (when absolute), then `~/.local/state/ibara/operator.sqlite`.

Opening refuses:

- a database, `-wal`, `-shm` or `-journal` file that is a symbolic link, not a regular file, not owned by you, hard-linked, or readable by group or others
- a parent directory that is not yours and mode 0700
- an ancestor that is a symbolic link, owned by anyone but you or root, or writable by others (root sticky directories such as `/tmp` excepted)
- an existing file without schema 2, its columns, its partial unique endpoint index and a valid `operator_instance_id`

### Naming a computer

Every command that names a computer takes the same names: `ibara client --computer` and `--rename-computer`, `ibara operator --computer`, `ibara mcp --computer`, the console's `--computer` and `wake`, and `computer_begin({computer})`. A computer answers to its label here and its host in any case (the host's first part alone too, such as `desk` for `desk.example.ts.net`), its `cmp_` id (the id `computer_status` and `computer_begin` show agents), its `computer_` id (this directory's) and its endpoint id. `directory::pick_computer` decides for all of them, among the verified computers; a `computer_` id of any computer in the directory is taken as it is. A name no computer answers to is refused with every computer as `"Name" (cmp_…, computer_…)`; a name more than one answers to (two computers with the same label) is refused as `AMBIGUOUS_TARGET` with those computers, so the person or agent uses an id. The console passes the plugin's `computer_` ids through without reading the directory.

### Routes

Every selected call binds a fresh envelope from the directory, then checks both credential files: each path component must be reached without a symbolic link, the identity key must be yours with no group or other bits, and the known-hosts file must be yours and not writable by group or others. The ssh argv is fixed: `-F /dev/null`, batch mode, `HostKeyAlias=<endpoint_id>`, no agent, no forwarding, no proxy. MCP and transfer log in as `ibara-agent`; operator calls log in as `ibara-op-<principal>`. `IBARA_TRANSPORT_ROUTE_V1` is set in ssh's own environment only. Unit tests hold the argv of every route as a golden string written from the Node source.

`ibara control` is not used by this version: it says so and exits 64. The legacy transfer route (`ibara client --operator`) still reads `$IBARA_STATION_DESCRIPTOR` or `~/.config/ibara/station.json` and runs `tailscale ssh <operator_account>@<node> "'computerctl' 'transfer-session'"`, each argument quoted as POSIX shell data.

### Operator calls and the preview service

`checked_reply` refuses any reply whose `endpoint_id`, `controller_epoch` (any valid epoch for `session`) or `authorization_generation` differs from the binding. A target refusal becomes `CODE: message`.

`OperatorSessions` keeps one long-lived `operator-v1` route per computer. `ibara operator --serve` uses it, and the operator-side console service in `ibarad` can use it in-process with `call(computer, epoch, op, fields)`:

- each call rebinds from the directory; a failed bind closes that computer's session
- a changed binding key (environment, computer, endpoint, binding revision, grant generation, route) closes the old session and opens a new one
- calls on one session run one at a time, with a 10 second deadline
- a timeout, end of file, a line over 2 MiB, an unrequested line or a reply for the wrong identity force-closes the session; a target refusal keeps it
- a session closes 30 seconds after its last reply; closing ends stdin, then sends SIGTERM to the ssh process group after 2 seconds, or at once when forced
- `take_control` and `handback` (up to 170 seconds) use their own route, so previews keep flowing during a control transition; so do `files_publish` (a sent file's final check) and `files_begin_download` (a fetched file's digest), which read the whole file, and which the target's `operator-v1` relay allows 150 seconds instead of 6

### The MCP relay

`ibara mcp --directory-db FILE --computer NAME` checks its computer at startup and exits 2 if it is unusable or the name is unknown or shared, as the Node wrapper did. `ibara mcp [--directory-db FILE]` without `--computer` covers every verified computer in the directory; it reads the directory at each call, so a computer added mid-session is usable at once. Both answer `initialize`, `ping` and `tools/list` from `crate::mcp` without contacting anything. A call opens that computer's route (one per computer, kept for the session), repeats the harness's own `initialize` there, and relays calls from then on with the relay's own JSON-RPC ids. Cancellations are passed on with the rewritten id; target notifications are passed back unchanged. Each answer is put in the console's words: where the computer names itself (the situation line, its fleet row, begin's `computer`, a computer ref's summary, hints), the relay puts the label its person gave it in this directory, read at each call, so a console rename reaches agents at once and whatever ibara the computer runs.

Without `--computer`, `computer_status()` asks every computer at once (up to 20 seconds) and lists each as it describes itself; one that cannot be reached is listed as `offline` with ssh's reason. `help:` refs are answered locally. `computer_begin({computer})` takes any name above (see Naming a computer), is optional with one computer, and passes the `cmp_` id on. A `task_ref` (or a status `ref`) goes to the computer that handed it out, the only computer, or the one that reports it open when asked. `computer_procedures` goes to the computer of the latest task, else the first. The legacy single-station MCP route is gone.

The first ok `computer_begin` through either form writes `{"first_task_done": true, "first_task_at": …}` to `onboarding.json` in the operator state directory (`$XDG_STATE_HOME/ibara` or `~/.local/state/ibara`).

A route that cannot open answers each waiting call with a `SESSION_UNAVAILABLE` tool result (`retry_safe: true`) that names ssh's last diagnostic. A route that closes under a call answers it with `SESSION_UNAVAILABLE` and `requires_reconciliation: true`, because the call may have run. The next call tries the route again. After the harness closes stdin, calls already sent get up to 120 seconds to answer.

`tests/operator.rs` runs the real binary with a fake `ssh` on `PATH` to prove the relay spawns nothing before the first call, exactly one route per computer afterwards, and the fleet routing above.

### Connecting agents

An agent connects itself, so ibara has no code for any particular agent program and writes no agent's files. The person pastes one prompt to their agent, `onboarding::CONNECT_PROMPT` (the only copy of its text). It asks the agent for three things: add the command `ibara mcp` to its own MCP settings as a user-level server named `ibara`, replacing any older `ibara` server and keeping everything else; link `/usr/share/ibara/skills/ibara` (core `skills/ibara/SKILL.md`, installed by the package) into its skills folder as `ibara`, leaving any other `ibara` skill in place and saying so; and keep a marked block (`<!-- ibara:start -->` … `<!-- ibara:end -->`) in its user-level instructions file, which says when to use ibara and names the skill's path for harnesses without skills. Then it loads the server, calls `computer_status`, and says which computers it can use and which steps it did. The link means a package update reaches every connected agent. Four layers carry the guidance, each saying only what the next can't: the block, read every session, says when to reach for ibara; the MCP `instructions`, sent at every connection, give the loop and the approval rule for harnesses that skip the rest; the skill says how to work well; and each reply's `situation` and `next` handle the moment.

The console shows the prompt on its Connect an Agent card with Copy Prompt, read through `connect-prompt` → `{prompt, first_task_done}`: the fleet shows the card until an agent has begun a task, and Add Computer always does. `ibara prompt` prints it on a computer without the console. `ibara mcp` with no computer reaches every added computer, so one entry serves them all. `ibara uninstall` cannot know which agents connected, so it tells the person to ask each one to remove the server, the skill link and the block.

### Deliberate differences from the Node tools

- `ibara mcp` no longer holds an ssh session open while the harness is idle, and it answers `tools/list` from contract 4 itself. A target that still runs the Node controller (contracts 2.0 and 3.0) will refuse contract 4 calls, so switch an operator to Rust only when its targets run `ibara agent-entry`.
- Credential and descriptor failures are reported directly. The Node client started a transport child that failed, then printed `Incomplete transfer response`.
- Publication links the verified partial with `linkat(AT_SYMLINK_FOLLOW)` on its held descriptor instead of spawning `/usr/bin/ln -L`.
- Transport timeouts read `spawnSync ssh ETIMEDOUT` and oversized output `spawnSync ssh ENOBUFS`, naming ssh rather than the `ibara-transport` script path.
- Reply lines are bounded: 8 MiB for transfer replies, 32 MiB for MCP route lines and 4 MiB for harness lines. The Node client had no bound.

### Start-up and shutdown

`ibarad` runs one current-thread Tokio runtime inside a `LocalSet`. It starts in the TypeScript order:

1. create the state, data and runtime directories (0700)
2. take `$STATE/controller.lock` (`{"pid","instanceId"}`, 0600, created exclusively; a lock left by a dead process is replaced)
3. read `policy.json`, `gateway.key` and `admin.sha256`
4. listen on `chrome.sock`
5. build and start the controller: new epoch, input reset, pause, viewer fencing, the Hyprland watch that replaces `output-watch.mjs`
6. listen on `controller.sock` (0660) and `admin.sock` (0600); a socket that still answers is never replaced, a stale file is
7. re-seal stored operator keys, then open the per-operator peer sockets
8. print `{"event":"controller_ready","instanceId","time"}` on stderr
9. start pairing: bind `pairing.sock`, then every 30 seconds read `tailscale status` and listen on each Tailscale address; each change prints `{"event":"pairing_listening","addresses","port"}`

On SIGTERM or SIGINT it pauses, shuts the controller down (close, cancel jobs, release input), closes the Chrome bridge, closes every socket and removes the socket files, then removes the lock if it is still its own. A start-up failure prints `{"event":"controller_failed","error"}` and exits 1.

### Sockets

| Socket | Credential | Accepted bodies | Connections |
|---|---|---|---|
| `controller.sock` | gateway bearer | `reconcile_display`, `heartbeat`, `disconnect`, `negotiate` (answers `{"contract_version":"4"}`), `transfer`, `call` | 32 |
| `controller.sock` | operator bearer (policy `operator_credentials` or `operator-authority.json`) | `{kind:"operator", principal:<that operator>, action}` only | (shared) |
| `admin.sock` | admin bearer | `{kind:"admin", action}` | 32 |
| `/run/ibara-operator/<p>.sock` | none; `SO_PEERCRED` uid must be the account's | `{kind:"operator", principal:<p>, action}` only | 8 |

- Only `POST /v1` is served. Headers must arrive within 10 seconds and the whole request within 90. Bodies over 24 MiB are refused from their `Content-Length` without being read.
- The request head is read in at most 16 KiB, so an unauthenticated client cannot make the server buffer more than that.
- While a request runs, the server watches for the caller hanging up. A hung-up `call` gets its `Cancel` fired: the controller stops at its next safe point (before the next step, in expectation waits and `computer_wait`) and never interrupts a dispatched effect. The server polls the work to the end and discards the reply, and gives the connection's place back at once, so abandoned requests cannot lock out new callers. Callers must not half-close their write side while waiting for the reply; none do.
- Every change to `operator-authority.json` (enrol, activate, revoke, pairing confirmation) runs behind one async lock. Enrolment reads the file again after awaiting the ACL tools, then changes and saves it with no await in between.
- A missing or wrong credential gets `403` and `{"error":{"code":"PERMISSION_DENIED","message":"Unauthorized transport."}}`, before the body is read.
- Every other failure is `200` with `{"result":{"kind":"response","contract_version":"2.0","status":"error","records":[],"error":{code,message,retry_safe,requires_reconciliation,recovery?}}}`. The remaining Node callers (lifecycle, viewer enrolment) parse exactly this.
- `call` takes `{principal, connectionId, tool, args, client_name}` and answers `{"result":<contract 4 envelope>,"images":[{"data","mimeType"}]}`.
- A peer socket exists only while its operator's route is open: before pairing, while a pairing waits for confirmation, and once enabled. It is created with mode 0600, then `setfacl -b` and `setfacl -m u:ibara-op-<p>:rw`, and `getfacl` must show exactly that one named user. Anything unproven fails closed and no socket appears.

### Pairing

Adding a computer needs no account names, addresses or terminal. Every target listens on each of its Tailscale addresses, TCP port 24247 (`tailnet::PAIRING_PORT`; `IBARA_PAIRING_PORT` overrides it, `IBARA_TAILSCALE_BIN` names another `tailscale`). Tailscale's WireGuard has authenticated the other node, so `tailscale whois` on the connection's source address says which computer and which login is asking; the only thing the other computer supplies is its `ssh-ed25519` public key, which it must prove it holds, and its `host_…` endpoint name.

Threat model: Tailscale names a computer, not the account on it, and any account can make a key. So an own computer is accepted without a person only when its own ibara (the target daemon, running as its desktop user) vouches that its desktop user's console made this very request. A program running as that desktop user counts as that person. Another local account (for example the restricted agent account) cannot reach the vouching socket; its request waits for a person like anyone else's. The vouch is only as strong as "the desktop user's ibara holds port 24247 on that computer": on a computer where ibara's target daemon is not running, another local account could bind the port and vouch for itself.

One JSON line each way per connection:

| Request | Answer |
|---|---|
| `{op:"probe"}` | `{ok:true, ibara:"ready", protocol:1}`, no identity check (the console's `tailnet` uses it) |
| `{op:"pair", public_key, endpoint_id, signed_at, signature, nonce?}` | `{ok, request_id, code:"NNN NNN", mode:"own_computer"\|"needs_approval", state, expires_at, route?, message?}` |
| `{op:"status"\|"cancel", request_id}` | the same shape; only for the computer that asked (same Tailscale stable node ID) |
| `{op:"vouch", fingerprint, nonce}` | `{ok:true, vouched}`: `true` once for a request this computer's console registered, and only to the computer it was registered for |

A `pair` request may also carry `invite` (a code, at most 32 characters of letters, digits, spaces and dashes); it is then signed too (see below) and a good code answers `mode:"invite"`.

- Proof of possession: `signature` is `ssh-keygen -Y sign -n ibara-pair` with the offered key over `pairing::statement` (`ibara-pair-v1`, the target address the asker dialed, the endpoint ID, the nonce or `-`, `signed_at` in milliseconds and, only when the request brings one, `invite <code>`). The target checks it with `ssh-keygen -Y verify` against allowed signers naming only the offered key (two files in a fresh 0700 directory under `$RUNTIME`). No signature: `UNSIGNED`. More than two minutes from the target's clock: `STALE_REQUEST`. Anything else wrong (another key, another target, a changed field): `BAD_SIGNATURE`. Nothing is stored for a refused request; `pairing_refused` is logged.
- Vouching: before asking another computer, the console registers `{op:"outgoing", fingerprint, target}` with its own target daemon over `pairing.sock` and gets a nonce (`pv_…`, single use, two minutes). For an own computer (same Tailscale user ID on both nodes, neither tagged) the target calls back the asker's pairing port from the address it was dialed on with `{op:"vouch", fingerprint, nonce}` (5 s). Vouched: accepted at once (`own_computer`). Not vouched (no nonce, no ibara there, no matching entry): `needs_approval`, and a person's Accept gives it everything an own computer gets. Asking again with the same key while that request waits, vouched this time, accepts it.
- A key this computer has already paired is also accepted at once when the same Tailscale computer (stable node ID) asks, or when its pairing predates tailnet pairing and recorded none; it gains nothing new. The owner's own computer re-pairing that way gains administer (`access_own_computer`) only under the same condition. Otherwise the request waits five minutes (`IBARA_TEST_PAIRING_WINDOW_MS` shortens it in tests) for a person on this computer. At most 16 requests wait at once, 2 per asking computer; the same computer asking again with the same key gets the same request.
- Accepting runs `authority::pair_operator`: the principal is the asking node's MagicDNS name (`vesper-1`), or `name-2` … `name-9` when another computer holds it or the name is `owner`, which is kept for the local owner (`computerctl`'s identity); the same node or key re-pairing replaces its own earlier pairing, and so does the owner's own computer re-pairing under a name whose pairing predates tailnet pairing and recorded no node (a computer reinstalled with its data deleted comes back under its old name and account instead of `name-2`). It issues the bearer, writes the authority record (with `operator_public_key` and the node's Tailscale identity) and calls `access_pair`: watch and files, as the reviewed pairing gave; control, agents and administer too when both computers belong to the same person. `access_sync` then sends the key to root with the projection (`keys`), which creates the `ibara-op-<p>` account, its key file and its agent gateway line.
- `route` (once `paired`): `principal`, `endpoint_id`, `controller_epoch`, `authorization_generation`, `host_key` (`/etc/agent-computer/ssh/host_ed25519.pub`, `IBARA_SSH_HOST_KEY`), `port` 2222 and `label` (the `name` in its settings, else the station's `display_label`, `IBARA_STATION_FILE`, else the Tailscale host name).
- This computer's answers go over `$RUNTIME/pairing.sock` (0600; this desktop user or root): `{op:"requests"}` → `{ok, requests:[{request_id, from_owner, from_computer, code, expires_at}]}`, `{op:"answer", request_id, answer:"accept"\|"decline"}` → `{ok, request_id, state}`, `{op:"outgoing", fingerprint, target}` → `{ok, nonce}`, and `{op:"pair", …}` (this computer adding itself, signed for its own address). The console's `pair-requests`, `pair-answer` and `pair-start`, and `ibara join`, use it.
- Sharing with a friend (`server::invites`): the person here chooses a level and an end (1 hour, 1 day, 1 week, or until revoked); `{op:"invite"}` on `pairing.sock` makes a single-use code of 8 characters from `23456789ABCDEFGHJKMNPQRSTWXYZ` (shown `XXXX-XXXX`) and keeps only its SHA-256 with the level and end in `$STATE/invites.json` (0600). Someone else's computer whose signed request carries a valid, unexpired, unused code is accepted without a person (`automatic`, `mode:"invite"`), `pair_operator` replaces any pairing its key had here, and `access_pair` gets exactly the level on every capability, each grant ending with the invite: Watch (watch), Use with Approval (watch; files, control and agents ask), Take Control (watch, files and control; agents ask); never administer. The access change's timeline sentence is `alex@example.com's Bench joined with an invite: Watch until Sep 28, 14:00.` (this computer's local time), which the owner's While you were away shows; the authority record keeps `invite:{id, level}`, the invite's `expires_at` and `tailscale.host_name`, and the operator `access` view marks another person's computer with `owner`, `computer_name` and `invite` for a caller who may administer. Anyone else gets only its own computer and agents: their rows, identities, pairing and grants, nothing about who else the computer is shared with. A wrong, used, expired or revoked code gets one refusal, `INVITE_REFUSED`, and counts against the asking computer (Tailscale stable node ID); after 5 in 10 minutes every code from it gets `TOO_MANY_TRIES` and nothing is used up. An own computer is added as always and uses no invite, whatever it sends. An invite is claimed in memory while its pairing runs and written as used (`{at, principal, fingerprint, login, computer}`) once it finishes. `{op:"invites"}` lists them without codes; an invite whose end passed leaves the file. `{op:"invite_revoke", id}` deletes it and, if used, calls `access_unpair` for that friend's principal while its current pairing still holds the key the invite enrolled and was made by that invite (the authority record's `invite.id`), under the authority lock. A friend's computer upgraded with a newer invite keeps the same principal and key, so revoking the older, used invite then ends nothing (`ended: false`). Events: `invite_created`, `invite_revoked`, `invite_revoke_failed`.
- Requests live only in memory; a restart forgets them. Events: `pairing_requested` (with `own_computer` and `automatic`), `pairing_refused`, `pairing_accepted`, `pairing_declined`, `pairing_failed` (with the real error), `pairing_listen_failed`, `pairing_tailscale_unavailable`.

`agent-entry` reads `SSH_ORIGINAL_COMMAND`:

- `mcp`: an MCP server on stdio. `initialize`, `ping` and `tools/list` are answered locally from `crate::mcp`. Each `tools/call` goes to `controller.sock` with the gateway bearer, read again for every request. Its deadline comes from its arguments: `computer_wait` gets `deadline_ms` plus 30 seconds; `computer_act` and `browser_act` get 15 seconds per step plus each expectation's `within_ms` (default 5 seconds, `quiet_ms` plus 3 seconds for `settled`, at most 120 seconds), typing time and 30 seconds; a foreground `computer_exec` gets its `timeout_ms` (30 minutes when absent) plus 30 seconds; everything else, and at least, 90 seconds. When the deadline passes, the session closes the request, which cancels the call on the controller. Every 5 seconds the session asks its client whether it is still there (an MCP `ping`; ibara's relay answers it, even during a long call). A heartbeat goes every 30 seconds, and at once when the client stops or starts answering again, with `answering`: false once the client has said nothing for 15 seconds. End of input or SIGTERM sends `disconnect`. When nothing listens on `controller.sock` yet (the socket is missing or refuses: `ibarad` is starting or restarting), nothing was sent: the call answers `SESSION_UNAVAILABLE` "ibara on <host> is starting; try again in a few seconds." with `retry_safe: true`, a `next` that says to make the same call again, and the situation line `<host> · ibara is starting`. Any later transport failure may have reached the controller: it becomes an error envelope with `requires_reconciliation: true` whose situation line reads `<host> · controller unavailable`.
- `transfer-v1`: the transfer line relay (2 MiB lines, `DELIVERY_UNAVAILABLE` on failure, `end_transfer` at the end).
- `operator-v1`: the operator line relay over the peer socket, or over `controller.sock` with the fourth argument as the operator bearer file. `pairing_confirm` must carry the pinned fingerprint: the fifth argument, else `/etc/ibara-operator/fingerprints.json` (root-owned, not group or other writable). With `--legacy` the pin comes from the one matching `restrict,command="/usr/local/libexec-ibara-entry <p>" ssh-ed25519 …` line of `/etc/agent-computer/ssh/authorized_keys`, falling back to `fingerprints.json` only when that file cannot be read.
- anything else: `Only mcp, transfer-v1 and operator-v1 are supported.` and exit 64. A malformed principal also exits 64.

`ibara admin` keeps `computerctl`'s grammar, usage text (as `Usage: ibara admin …`), validation before any contact, pretty-printed `{"result":…}` output, exit 1 on `error` or `result.status == "error"`, the `transfer-session` line protocol and the root-only `approve_procedure` installation. It adds `attention [STATE] [TASK_REF]` and `answer_attention ATT_REF ANSWER [ANSWERED_BY]`, the engine's approval operations.

### Deliberate differences from the TypeScript

- Contract 4 has no negotiation: `negotiate` always answers `"4"`, `call` carries `client_name` from the MCP `clientInfo`, and the agent entry no longer validates input or negotiates locally. The controller validates and answers every call.
- The legacy error envelope always says `contract_version: "2.0"`, the TypeScript default for every connection that never negotiated. Only MCP sessions negotiated 3.0, and they now go through `agent-entry`.
- A corrupt `operator-authority.json` refuses every operator bearer and closes every peer route. In TypeScript it threw outside the request handler's `try`.
- If `policy.json` or `operator-authority.json` cannot be read, the controller sees no operator grants, so operator calls are refused. TypeScript threw an unsanitised error.
- A filesystem failure while enrolling reports `INTERNAL_ERROR` with the `io:` message instead of the generic sanitised text.
- A request that is too slow is closed without a `408`, and a connection over the limit is closed as soon as it is accepted.
- `transfer.js --operator` is not ported: no forced command ever passed it.
- `ibara backup-journals` prints its report as one JSON line.
- The lock is removed when start-up fails after taking it, and a SIGTERM during start-up is handled as a clean shutdown once start-up finishes.

### Journal view

Storage never opens `journal.sqlite`. The controller engine installs a `JournalView` with `set_authority_policy`. It provides `read_task` (`requireReadableTask`), `collector`, `task_state`, `has_unresolved` (the artifact-expiry rule) and `has_unsettled` (the job-log rule). Without a view nothing expires and no logs are pruned, as in the TypeScript without an authority policy. A journal error always keeps bytes and logs.

### Schema

Version 0 is the TypeScript schema, unchanged. Version 1 adds `file_writers(task_ref, path, operation_ref, sha256, size_bytes, written_at)`: the operation that last wrote each workspace path through `computer_files`. Contract 4 `publish` names that operation as the producer only while the file still holds the bytes it wrote. Otherwise it claims no author: the producer is an opaque `producer_` reference, as the TypeScript produced. The Node controller can still open a migrated file.

`src/storage/tests.rs` lists its failure cases at the top. `real_storage_databases_open_and_keep_their_rows` opens copies of each computer's databases in `fixtures/private/<name>/` (never committed; skipped when absent) and checks that every row survives, apart from `jobs.updated_at`, which recovery rewrites.

### Deliberate differences from the TypeScript

- **Operator upload jobs are read from the table when needed** instead of all being loaded at start. A `publishing` row is rewritten as `uncertain` at open, which is the state the TypeScript gave it in memory.
- **Operator downloads are bounded:** at most 64 at once, and one idle for 5 minutes is dropped. The TypeScript kept every abandoned download's descriptor open.
- **Only live jobs stay in memory:** running jobs, and unknown jobs whose termination is not confirmed. `request_settled` therefore reads the latest job for the request from the store, so a job that finished before a restart still settles its request. The TypeScript searched memory only, and answered `pending` after a restart.
- **Spawn failures:** a failure other than `ENOENT` is `failed` with exit code 126 and confirmed termination, because nothing ran. The TypeScript recorded it as `unknown` with unconfirmed termination, which left the task unsettled until restart. `ENOENT` is still 127.
- **Output cap:** it keeps exactly the first `max_output_chars × 4` bytes across stdout and stderr. The TypeScript dropped the whole read chunk that crossed the cap.
- **Hashing and copying:** publication, import and inbox completion hash the bytes as they copy them, and record that digest. Inbox completion streams the copy instead of reading the file into memory. The TypeScript hashed first and then copied, so a file changing in between got a digest of other bytes.
- **Refusal codes:** a symlink, a missing path or a non-directory met while walking a workspace, a publish source or an overwrite target is refused as `PERMISSION_DENIED` or `INVALID_ARGUMENT`. The TypeScript surfaced some of these as raw `ELOOP`, `ENOENT` or `ENOTDIR` errors.
- **FIFOs:** read-only opens add `O_NONBLOCK`, so a FIFO is refused by the type check instead of hanging the process.
- **Job-log pruning** runs when the journal view is installed and on every `capabilities()`, not in the constructor.
- **Job-log pruning** also only asks the journal about tasks that have a job with retained output. The outcome is the same.
- **Contract 4 additions:** `write` also takes `base64` (at most `chunk_bytes` decoded bytes). `exec` also takes `command[]` and `background`. A `send` returns the artifact and a `delivery_obligation` record, which the engine adds to the task's deliveries.
- **Dates:** `Date.parse` accepts ISO dates and date-times with `Z` or an offset. An offset-less date-time (JavaScript local time) is refused.
- **Ordering:** `localeCompare` for equal-score procedure titles is approximated without ICU: case-insensitive, then lower case first.
- **Size:** a staged upload size must be a whole number of bytes.
- **Serialisation:** `serde_json` is built with `preserve_order`, because procedure digests hash `JSON.stringify(definition)` in stored key order.

### Running it

`ibarad` builds options with `ControllerOptions::live(LiveConfig {…})`, then `Rc::new(Controller::new(options)?)` and `controller.start().await` inside its `LocalSet`. `new` opens the journal and rotates the epoch. `start` resets input, keeps the computer awake (`keep_awake`; it logs `stay_awake_on` when it turned Stay Awake on), pauses for the system (revoking any authority from before the restart), ends any stream an earlier `ibarad` left (`initialize_viewer`), and starts the 15 s viewer grant sweep, the 1 s check that stops an idle stream, a 2 s lease check (idle expiry after 300 s without a heartbeat, 30 s disconnect grace), the watchdog and the display reconcile loop fed by Hyprland events. Nothing in the engine holds a `RefCell` borrow across an `.await`.

`control_state.pause_origin` (core schema 5) records who paused: a person (`computerctl pause`, the operator-route `pause`, or taking control) or the system (start, shutdown, viewer faults, a restart during a lease). A system pause never replaces a person's, and a resume clears it. The watchdog (`watchdog.rs`) runs every 5 s: it creates `IbaraVirtual` when the session has no output and no display event started the reconcile loop, runs `initialize_viewer` again after a viewer fault (it revokes and ends any stream left behind), and settles unsettled work once nothing has run for 30 s. It then resumes, writing an `auto_resumed` timeline event, when the pause is the system's, the controller is settled, the viewer is neither faulted nor held and a display exists. Each repair writes a `repair` event. Failed repairs back off from 10 s to 5 minutes; after three, operator and admin `status` show `repair.needs_person {code, message, fix}` until the problem clears. Handing back resumes agents unless the pause before taking control, or one made while holding it, was a person's; if the hand-back leaves work unsettled, the pause becomes the system's so the watchdog can finish.

`reconcile_display` creates `IbaraVirtual` even while the controller is paused (every start and every viewer fault pauses, which also sets `human_control`) or unsettled: it takes nothing from a person, and a computer that started without a display needs it before its viewer can settle. Removing it waits until the controller is resumed and settled. Under a lease, while a person holds control through the viewer, or while control is being settled, nothing changes: a settlement counts an effect queued behind it as work that may still run, so a display change that waited for a task's lease used to run during that task's finish and leave the computer unsettled for the watchdog's 30 s grace. A deferred reconcile is retried every 5 s.

### Take Control

The person taking control (the operator route's `take_control`) gets the desktop through `ibara-stream`, started by `ibarad` on demand and admitted only with one-time tickets:

- **Viewer identity.** Each console has one viewer certificate, made by `ibara-view --create-identity` in `~/.local/state/ibara/viewer`. Before `take_control` and `viewer_ticket` the console sends `viewer_register {viewer_cert_sha256}`; the controller authorizes it (an active pairing and the pinned endpoint and epoch, no access gate) and the server saves `viewer: {cert_sha256, generation}` on the operator's record in `operator-authority.json`, for that pairing generation only. No PIN and no restart. A different certificate ends the stream the old one holds; a new pairing starts without one.
- **Taking control** (serialized under the viewer lock) needs `control` allowed, or asked and approved: the access gate runs before anything else. A locked screen does not refuse it (`control_ready`): the person types their password in the viewer, while agents stay refused until the screen is unlocked. Then the stream is revoked (ending any earlier holder's viewer, closing admission and waiting until its held keys are released) while agents are paused and settled; both must finish. Then the stream starts if it is not running, opens a new generation and gets a ticket (64 hex, 60 s) bound to the registered certificate. The reply adds `stream {ticket, expires_in_ms, server_cert_sha256, http_port, https_port, width, height, fps, bitrate_kbps, encoder, software_cap}`. A revoke that fails or cannot prove the keys released mints nothing: the stream is ended and the computer stays paused and unsettled for the watchdog.
- **Closing the viewer** ends its stream: every second an idle stream (no live ticket, no launch waiting, no stream) is stopped. The holder keeps control and the computer stays paused. `viewer_ticket` (the console's Open Viewer; the holder only) starts it again with a fresh ticket.
- **Hand back** revokes and stops the stream, then resumes agents unless a person paused them before taking control or while holding it; when earlier work is still unsettled it leaves a system pause for the watchdog. The reply's `pause_origin` says who still pauses agents (`null`: they can work again), and `agent_resumed` stays `false`: no agent's control is given back. `status` names why agents wait while only ibara paused the computer in `system_wait` (`starting`, `settling`, `needs_person`, `resume_off`, else `null`), and says `locked: true` while Hyprland shows the session lock (`false` when unlocked or unreadable), so the console says Locked, not offline; it still lists the displays then. Grant expiry, a denial, unpairing and a new viewer certificate end control the same way (`revoke_viewer_operator`).
- **`LiveStream`** writes `<state>/stream/ibara-stream.conf` (the Tailscale IPv4 address from `tailscale ip -4`, base port 47989, `capture = wlr`, both encryption modes 2), keeps apps, state, credentials, its TLS key and certificate and `ibara-stream.log` there, and talks to `<state>/stream/control.sock`. The child gets `PR_SET_PDEATHSIG` and is killed when the port drops. `IBARA_STREAM_BIN`, `IBARA_STREAM_BIND` and `IBARA_STREAM_PORT` override the program, address and base port. Without `/usr/bin/ibara-stream`, `status` reports `interactive_control: unsupported_without_verified_viewer_adapter`.
- **The shared clipboard** (`clipboard_get {since, offset?}`, `clipboard_set {mime, size, sha256, offset, data_b64}`) answers only the holder, and only while this computer's `shared_clipboard` setting is on (else `{enabled: false}`). A `wl-paste --watch` watcher runs from the holder's first `clipboard_get` until control ends; what the clipboard held when it started is not shared, and a clip the holder set is not sent back (the last known content's hash is kept). Text and PNG up to 8 MiB travel in pieces of at most 768 KiB; when a newer, shorter copy replaced the entry being fetched, an offset past its end gets `{enabled: true, seq}` with no clip and the console starts the new entry from 0. A watcher is installed only if control did not change while the clipboard was first read, and taking control forgets every entry from before. Nothing about the clipboard is journalled or put in the timeline.

### Operations, replay and approvals

- Every effect is an operation written as `running` before dispatch. An act's first step shares the call's operation (its `request_id`); later steps are `<request_id>#<n>`, which an agent's own ids cannot collide with. The call's whole result, or its error, is stored on the first operation, so repeating the `request_id` with the same arguments returns it and dispatches nothing, from any session. Each operation records its session (`operations.session`, the connection id of the `ibara mcp` process; rows from before have none). Different arguments under the same `request_id` are `REQUEST_CONFLICT` in the session that used it, and while its request has not finished (no stored result, a step running or of unknown outcome, or held for approval). From another session, once it has finished, they are a new request: the earlier operation and its steps move to `<request_id>~<operation_ref>` (steps keep `#<n>`), where a retry of the earlier request still replays.
- An act stops at the first step that is unmet, unknown, refused or held; later steps are `not_run`. An unknown step is never run again, including after a restart, when the journal reports it from its operation.
- Each step has an effect class. Desktop and browser actions are `change` unless the agent declares `send`, `spend` or `destructive`; file writes that overwrite are `destructive`, sends are `send`. The rule per class comes from `policy.json` `effect_rules`, else allow `observe` and `change` and ask for the rest. An ask raises an approval attention item and returns `pending`, recording the step's resolved target (window address and pid, element identity, logical point, key combo or a digest of the text). Repeating the same `request_id` after a person approves runs that step under the same control generation only, and only if it resolves to the same target; otherwise it is held again with a new attention item ("the target changed since it was approved"). A refusal, an expiry or a change of control ends it as `not_run`. The item's `question` is what a person reads (`controller/approval.rs`): who asks (the task's agent), what the step does in plain words, in which app and on which page (host and path from the browser's focused tab, never the query) or window title, why it asks first (sends something, spends money, deletes or overwrites something) and the task's goal when it is at most 120 characters, never JSON, window addresses, process ids or tool names. Its `details` (a JSON column read past by older builds) carry the structured request: the agent, task, tool, effect class, the step and its exact target, and where. Adding that column expires approvals still open from before, which were worded as code.
- `call` takes a `Cancel` that the server fires when the caller goes away. The call stops at its next safe point: before a step (later steps are `not_run`), in an expectation wait (the step is `unmet`, "the caller went away") and in `computer_wait` (`pending`). A dispatched effect always runs to completion, and the outcome is stored for replay. The server keeps polling the future rather than dropping it.
- Repeating a `request_id` while that call is still queued or running answers `pending` at once, with `{op_ref, state: "running"}`, instead of waiting behind it. A step left `running` without a live call is reported as "the call ended during this step" within the same epoch, and "the controller restarted" after a restart.
- `admin` gains `attention {state?, task_ref?}` and `answer_attention {att_ref, answer, answered_by?}` so the console and tests can answer (`approve`, `approved`, `yes`, `allow` or `ok` approve).

### What agents see

- The situation line names the computer, who controls it, the task and its checks met, unknown outcomes, open attention items, memory pressure when tight, and the frame revision.
- `since` lists controller events for the session's task, and window, focus and display events only for the session holding control. At most 12 lines.
- A frame lists windows (`w1`…), the dialog in front, accessibility elements of the focused or named window (`e12 button "Save" enabled · dialog "Save As"`), Chrome tabs, and app notes about routes that were refused on that surface. Choices refer to the same frame's ids and are resolved against it when chosen. A typing or key choice is for the window it was offered for: if another window has taken the keyboard focus since the frame (a viewer or a terminal that opened), it is refused with `STALE_TARGET` and nothing sent, naming where the focus went. Typing into the focused window is not offered while a button or other control that takes no text has the keyboard focus. Launching an app the goal names is offered until the task has a window of that app; a window someone else left open does not count.
- `begin` returns the task's `workspace` path, so an agent can type it into a Save As dialog.
- In an act, a `window` expectation is met only by a window that appeared, or came to match, after the step. So is `dialog` with a title: a matching dialog left open from before the step does not count. `dialog` with `gone` means the dialog in front before the step closed; with a title, the matching dialog in front (else the first matching one) before the step. `computer_wait` waits for a state, so any matching window counts there.
- `finish` closes windows that appeared during the task's own steps and belong to them: for a launch, windows of the launched process tree or the app's window class; for other steps, windows of the process acted on. Windows a person opened meanwhile are not the task's. It closes them unless a person touched them (focus or title changes outside the task's effects, or a person taking control) or their title marks unsaved changes. A window is reported closed only once it has left the window list, checked every 100 ms for up to 2 s after the close requests; one still there is reported left open, "still open after the close request". ibara does not stop the app's process, because another of its windows may hold unsaved work.
- App notes record, per app, package version and surface: whether it has an accessibility tree, which routes worked or were refused, and which shortcut opened which dialog. A refusal becomes a note only when its error says it describes the app (`about: app`, today Cua's "needs exactly one editable text element" for text beyond ASCII); a refusal about one element or one step (a field that takes no focus, a window not yet focused, a person using the mouse) never does, and route notes recorded without that mark (by 0.1.0-4 and earlier) are not shown.

### Tests

`src/controller/tests.rs` drives the engine through `call`, `admin` and `operator_call` with a fake desktop and stream and a real journal and storage. Failure cases first: a failed begin replays its error; changed arguments conflict; an act replay dispatches nothing; a step after an unmet expectation does not run; an unknown step stops the sequence and is never replayed; a refused first step is an error that replays; a held send step runs once after approval; a typed check that cannot pass is refused at begin; control expires after five idle minutes; a restart makes a running step unknown; operator calls with a wrong epoch, generation or endpoint are denied; take-control against a stale owner or revision conflicts; a window open before a launch does not meet its window expectation; a dialog still open is not gone; typing is not offered while a button has the focus.

### Deliberate differences from the TypeScript

- **Contract 4 only.** No negotiation; `endpoint` answers `protocols: ["4"]`. Tasks written by the engine carry `contract_version "4"`; older tasks stay readable through `computer_status` and the admin views, whose completion projection still judges them by their claims and proofs.
- **Begin never reuses a lease.** An agent that already controls a task, over this connection or an earlier one that is gone, gets `BUSY` naming it, instead of the old task's brief.
- **An agent back over a new connection carries on at once.** The TypeScript bound control to one connection, so an agent whose network dropped was locked out by its own old session (still open on this computer until sshd noticed, then 30 s of disconnect grace) and told another agent controlled the computer. Now a call naming a task from the agent that began it (same pairing, same client name) moves that task's control to the calling connection, keeping its generation, once the old connection is gone: disconnected (in its grace), or its client has stopped answering the session's pings (its heartbeat says `answering: false`). Two live sessions of one client (two `codex` sessions on one computer) cannot take each other's control: to the second, the first one's control is another agent's, and begin's `BUSY` does not name its task; the old connection's heartbeats and disconnect no longer count, and work still running for it stops at its next authority check. Nothing moves while a person holds the computer or it is unsettled, nor control that already ended. The situation line and `computer_status` call such control `you (agent)`; `another agent` means another agent.
- **An unknown outcome does not fence the task.** It stops its own call, is never replayed and keeps `complete` false; the agent may continue with new requests after checking it.
- **Finish records what happened.** `outcome: complete` without every check met, every delivery verified and no unknown outcome is stored as `partial` with `complete: false`, rather than refused.
- **Lease deadlines are checked every 2 s** instead of by one timer per deadline.
- **A failed begin replays its own error.** The TypeScript answered `PERMISSION_DENIED` for the placeholder task.

### The socket

`$XDG_RUNTIME_DIR/ibara/ibarad.sock`. The directory is created or tightened to 0700 and must be ours; the socket is 0600, and a peer with another uid is dropped. A socket that still answers means another operator service is running, so start-up fails; a stale one is replaced. SIGTERM or SIGINT closes every operator session and removes the socket. `packaging/systemd/ibara-operator.service` is the user unit (`ExecStart=/usr/bin/ibarad --role operator`, `Restart=on-failure`, part of `graphical-session.target`).

One connection carries newline-delimited JSON, at most 64 KiB per request line:

- **Request** `{id, command, args}`. `command` and `args` are the bridge's argv after its global options. Older plugins also send `for_computer` and `station_descriptor`; both are ignored. A line without a usable `id` (1–256 characters, no control characters) is dropped; any other malformed request, including an unknown field, is answered with `INVALID_ARGUMENT`. There is no station and no administrator route: every computer is reached over its own pairing route. `status` always answers ready with data `{"station_configured": false}` for plugins that still poll it; the old station commands (`tasks`, `logs`, `maintenance`, `computerctl` reads…) are `Unknown command`.
- **Reply** `{id, envelope}`. `envelope` is exactly the bridge's envelope for that command, with `request_id` equal to `id`, so `StatusModel.js` parses it unchanged.
- **Event** `{event: "preview", computer_id, data}`. This answers `operator-observe`; `data` is the preview envelope and `data.request_id` is the request's id. The picture is not in the line. The envelope's `data.result.file` is the path of a PPM file and `data.result.bytes` its size, in place of the target's base64 `result.jpeg` (`result.png` from a computer from before). When the screen has not changed since the last picture, it names that picture's file again. While watch is Ask First on that computer and nobody has approved yet, the envelope is an error `CAPABILITY_UNAVAILABLE`, `Waiting for someone on <computer> to approve watching.`, which may be retried; `operator-status` then says `observation: "ask_first"` and lists the displays.

Requests run concurrently and are answered in completion order. At most 32 are in flight per connection (more are answered `BUSY`), 16 answer lines wait for the writer, and 8 connections are served. A request whose connection closes still runs to its own deadline, so an effect is never cut short, but its answer is dropped.

### What runs where

- **In-process:** the directory (read per request), rename, operator sessions and previews through `OperatorSessions` (one route per computer, idle-closed after 30 s), control transitions over their own route, human file transfers, collecting results through `client::collect` over the computer's operator route (`artifact_transfer`), magic packets (UDP broadcast to port 9).
- **Still spawned:** `tailscale status --json` and `tailscale whois --json` (pairing), `ssh-keyscan` (an added computer's host key, for `tailnet`), `ssh-keygen` (the operator key, created without a passphrase when `~/.ssh/ibara_agent_ed25519` is missing); `omarchy-file-select` for the chooser; `ip -j` (is this computer on a sleeping computer's network); `ibara-view --create-identity` once; `wl-paste --watch`, `wl-paste` and `wl-copy` while this console holds control of a computer.
- **Launched detached:** the viewer and terminals start in their own process group, inside a transient `systemd-run --user --scope` when `systemd-run` exists, so restarting `ibarad` never closes a viewer or terminal the person opened. The viewer's windows float, centred, at 1280×720 logical pixels (the largest 16:9 that fits a smaller output): right after the launch `hyprctl eval` gives Hyprland a `window.open` handler for the viewer's pid (`console/viewer.rs`), because Hyprland's exec rules reach only a process's first window and its window rules cannot match a pid. Omarchy's `apps/moonlight.lua` rule makes every Moonlight window full screen as it maps, before the handler runs, so the handler takes the window out of full screen before floating it. The person can still tile it or make it full screen.

**Take Control from the console.** `operator-control --op take_control` first registers this console's viewer (`viewer_register`). With the ticket in the reply it starts `ibara-view connect`, with a JSON bundle on its stdin (`v, computer_id, computer_name, host, http_port, https_port, server_cert_sha256, ticket, identity_dir, keys_chord` (`Super+Alt+Escape`)`, console_socket, controller_epoch, app, width, height, fps, bitrate_kbps`), and starts sharing the clipboard with that computer (`console/clipboard.rs`: its own `wl-paste --watch`, and `clipboard_get` every second, every ten seconds while the computer has sharing off; only `PERMISSION_DENIED` or `STALE_TARGET` from the computer ends it, other refusals are tried again). The envelope returned to the plugin never carries the ticket. `open-viewer --computer ID [--epoch E]` asks for a fresh ticket (`viewer_ticket`). Hand Back stops the clipboard and ends the viewer this console started (checked by process name). `ibara-view` is `IBARA_VIEW_BIN`, else the first ELF `ibara-view` on `PATH`. A computer from before ibara-view answers `take_control` without `stream` and does not know `viewer_ticket`; it gets Moonlight, as before.

Previews of one computer run one at a time: a request that arrives while another is in flight waits for it within its own 15-second deadline. No envelope is kept once its line is written. On Vesper the service uses about 4 MiB PSS, idle or streaming two computers' previews. Requests run on one thread; preview pictures are scaled and written on a second.

### Preview files

Each preview picture is written to a file for the shell's `Image` to read. A base64 frame in the JSON line was the console's largest memory cost: the shell's script engine held the line, the parsed string and a `data:` URL for each frame, and kept the heap growth. On Tulip1 at 2 GiB, the picture stream was 32 of the 80 MiB an open console cost, and 14 of the 31 MiB it kept after closing.

The file is raw PPM (P6), already at the size the console shows it, so the shell reads it on its GUI thread. Qt's background image reader kept about 15 MiB in the shell after the console closed. Reading a 1280×720 PNG on the GUI thread stopped the shell for 51 to 83 ms on Tulip1; a 1152×648 PPM takes 4 to 6 ms and a tile 2 to 4 ms. The shell never reads JPEG: only `ibarad` does.

- **On the network:** the console asks for `format: "jpeg"`, and the target sends the picture as `result.jpeg`, about a tenth of the same picture as PNG. A computer from before ignores the field and sends `result.png`, which the console still reads; a console from before asks for nothing and gets PNG.
- **A still screen is sent once:** each answer carries `digest`, the SHA-256 of the encoded picture. The console keeps the last picture's digest, file and shown size for each computer and quality, and sends `previous: <digest>` with the next request for the same display and shown size while that file is still there. A target whose new picture has that digest answers `unchanged: true` without the picture, and the console answers with the same file, which the shell already shows, so it reads nothing. A changed shown size, another display, or a file released or pruned since, sends no digest, and the picture comes in full. An `unchanged` answer for a file released while the request was out is `CAPABILITY_UNAVAILABLE`, `The preview carried no picture.`, and the next picture comes in full.
- **Where:** `$XDG_RUNTIME_DIR/ibara/previews/<computer>-<quality>-<n>.ppm`, beside the socket. `<n>` counts up from 0 each time the service starts.
- **Shown size:** `operator-observe` takes `--width W --height H`, the size in device pixels the plugin shows that quality at (each 16 to 4096; one without the other, or a value outside that range, is refused with `Selected observation size is invalid.`). Without them, a tile fits 448×256 and a selected frame 1152×648. The picture is scaled to fit inside that size, keeping its shape and never enlarged, by averaging the pixels each output pixel covers.
- **Permissions:** the directory is 0700 and must be yours. Each file is created new with mode 0600. If the directory exists but is not a private directory owned by you, `ibarad --role operator` exits at start with `<path> is not a private directory owned by this user.`
- **Size:** a tile frame may carry at most 350,000 base64 characters (about 256 KiB of JPEG or PNG) and 480×270 pixels; a selected frame 1,400,000 characters (about 1 MiB) and 1280×720. So a file is at most 388,815 bytes for a tile and 2,764,816 for a selected frame. A larger frame, an invalid picture or a failed write answers `CAPABILITY_UNAVAILABLE` and writes nothing.
- **Cost:** on Vesper, decoding, scaling and writing a 1280×720 PNG frame takes about 15 ms for 1152×648 and 10 ms for a tile, on the writer thread. It decodes one frame at a time and frees its buffers after each. `ibarad` fixes glibc's mmap threshold at 128 KiB, so each buffer of that size or more goes back to the system when freed. Without it, the service kept 9 MiB more after 250 frames; with it, 0.3 MiB.
- **Pruning:** after each write, only the newest three frames of that computer and quality are kept, because an image cross-fades between two.
- **`preview-release <file name>…`:** the plugin sends this when the console closes, naming the base names of frames its sessions still show. `ibarad` deletes every other frame file, including one that arrived after the close. A reopened wall then shows its last pictures at once. The reply is `{"released": true}`.
- **Start and stop:** the service empties the directory when it starts and when it stops.

Previews stay transient and are never task evidence: an agent's evidence comes from its own observations and the replay pictures.

### Live video

Live Video (Preview) is opt-in (`live_video`, off). The target encodes its screen as H.264 in MPEG-TS (`observe_video`); the console writes the bytes to a named pipe the shell's `MediaPlayer` reads.

- **On the target:** `status` carries `video: {capable, reason}` (`reason` in plain words, and "Checking whether this computer can stream video." until the first probe has finished). `observe_video {width, height, cursor, display_id?}` answers `{cursor, data (base64), reset, ended, width, height}` plus the binding. It passes the same watch gate and `authorize()` as `observe` on every call, before and after reading; while a person holds control it stops the encoders and answers `CAPABILITY_UNAVAILABLE` (`reason: control_held`), and a locked screen stops them too. Taking control stops them at once. See the desktop layer's `observe_video`.
- **`video open COMPUTER --width W --height H`** (console command, and `ibara video open …`, which asks the running console service and prints the envelope's data as JSON): `{"path": "…/previews/video-<computer>-<W>x<H>-<n>.ts", "state": "starting"|"playing"}`. The size is clamped to at most 640×360 and at least 16, in even numbers. Asking again returns the same path and renews the stream; a stream not asked for within 10 s closes. `playing` means bytes of the current stream reached a reader. When `live_video` is off the answer is `{"unsupported": "Live Video is off in Settings."}` (and that computer's stream closes); when the computer answered `VIDEO_UNSUPPORTED`, it is `{"unsupported": "<its plain words>"}` for the next 60 s.
- **`video close COMPUTER`**: `{"closed": true}`; the stream and its FIFO go at once.
- **Live, not late:** a player plays what it is given at the pace it was recorded, so bytes kept for it would keep it behind by as long as they waited (a 17 s lag was measured when they were). Nothing is asked for or kept while no reader has the FIFO open. Once one opens it, the stream calls `observe_video {width, height, cursor}` about every 0.25 s (2 s after a failed call), starting without a cursor, over its own session to that computer, separate from the one status and pictures use; it binds its controller epoch with `session` and binds again after any failure. The target answers a read without a cursor from an encoder at most 1 s old, starting a new one otherwise, and its encoder makes a keyframe every 15 frames (about 1 s). The pipe's buffer is 16 KiB.
- **A new stream:** when the target answers `reset`, when an encoder that sent bytes answers `ended`, when the reader closes the pipe, or when bytes have waited for the reader for more than 2 s (or pass 4 MiB), the console ends the stream (its reader reads to the end) and replaces the FIFO at the same path; the next reader starts without a cursor, so its bytes start from a fresh encoder's first keyframe. The shell reopens the path on the end of a stream.
- **Closing:** before a FIFO is removed or replaced, the console opens and closes a writer end without blocking, so a reader still waiting in a blocking `open` reads the end of the stream instead of hanging. `preview-release` removes only `.ppm` frames, never a FIFO. The service closes every stream when it stops.

### Tests

`tests/console.rs` runs the real `ibarad --role operator` with a fake `ssh` (the selected operator route) on `PATH`: the socket is private and a second service refuses to start; a line without an id is dropped and one without a command is refused by id; a reply for another epoch is `OPERATOR_REFUSED`; an old plugin's station command is unknown and its `status` hears there is no station; then `status`, `directory`, `operator-session`, `operator-status` and preview events over one route.

`tests/everyday.rs` (the `tests/pairing.rs` world, `tests/support/`) pairs real consoles and targets and drives logs, health, settings (a hand edit picked up live), power through the real `ibara power-system` with fake `systemctl`/`iw`, theme sending, repairs, approvals from two computers, watch set to Ask First (one approval for a sitting; an access change or a Decline), `away`/`away-seen`/`ibara away`, and wake packets caught on a UDP socket. The failure cases are listed at the top of the file and of each test.

`tests/watch.rs` (the same world) gives the target a desktop whose screen is a PPM file behind a fake `grim`, and copies every line between console and target to a log: the first picture crosses as JPEG and lands as a PPM of the shown size with the screen's pixels; a still screen crosses as a few hundred bytes and names the same file; a changed screen, another shown size and a released file each bring a new picture.

### Deliberate differences from the bridge

- **`request_id` is always the request's id,** even when the request fails before a station is chosen. The bridge replaced an id outside `^[A-Za-z0-9_.:-]{1,128}$` (the plugin's file-list ids contain `#`) with a random one.
- **Status, task, file and preview reads share the computer's long-lived route.** The bridge started a new `ibara-operator` (and ssh) for every one-shot read. A lost route reads `Selected operator transport timed out.` or `…closed.`, which the plugin already treats as offline.
- **`upload` is not ported.** The console never sent it; it answers `Unknown command upload.`
- **No station commands.** Everything the bridge ran through `tailscale ssh ADMIN@NODE computerctl …` runs over the computer's pairing route instead (see Everyday commands).

## Package, setup and updates

`packaging/` builds the `ibara` Arch package (`PKGBUILD`, run by `release.sh`). `release.sh` also builds `ibara-stream` and `ibara-view` at the same version from the forks' `ibara` branches (their `packaging/ibara/PKGBUILD`: the slim `IBARA_STREAM` build installs `/usr/bin/ibara-stream` and `/usr/share/ibara-stream/`; the viewer only `/usr/bin/ibara-view`), signs the release manifest naming all three, writes a source tarball of core, plugin and both forks, and writes the one-line installer from `install.sh`. `ibara` depends on exactly that `ibara-stream` and `ibara-view`, so Take Control works on every install. The package holds `/usr/lib/ibara` (`bin/ibara`, `bin/ibarad`, `ops/`, Cua's plugin source, the browser page reader), `/usr/bin` links and `/usr/bin/computerctl`, the system units `ibara-agent-sshd.service`, `ibara-access.socket` and `ibara-power.socket` (with their `@` services) and `ibara-unattended-boot.service`, the user units `agent-computer.service` and `ibara-operator.service`, sysusers (`ibara-agent`, `ibara-runtime`), tmpfiles, the `/dev/uinput` rule, the pacman hooks (`ibara-refresh.hook`: set up again after `ibara` is installed or upgraded, without turning Tailscale back on; `ibara-cua.hook`: only rebuild Cua's plugin after Hyprland or GCC changes), the agents' skill in `/usr/share/ibara/skills/ibara` and the console plugin in `/usr/share/ibara/omarchy-plugin`. `packaging/release.env` holds the two values the maintainer chooses: the release address and the public release key; both are compiled in.

Releases are GitHub releases of `MayberryDT/ibara`. `IBARA_BASE_URL` in `packaging/release.env` is `https://github.com/MayberryDT/ibara/releases/latest/download`: GitHub redirects each file there, over HTTPS, to the release marked Latest and then to its asset host, which the installer's and `ibara update`'s curl follow (`--proto-redir =https`). The plugin's `ibaraBaseUrl` names the same address. `packaging/publish.sh [--publish] [--sign-key KEY] [--private-markers FILE] [--out DIR] --plugin DIR --stream DIR --view DIR --notes FILE VERSION` runs `release.sh` with the signing key in `~/.config/ibara-release/ibara-release`, checks every file again (the signature, each package's digest, size and version, the channel built into the packaged `ibara`, the installer), then uploads the three packages, the source tarball, `install`, `stable.json` and `stable.json.sig` with `gh release create` as release `vVERSION` at this checkout's commit, which must already be pushed, and compares the uploaded files with its own by size and SHA-256. Before building, `release.sh` refuses a release when the tree of core, the plugin or either fork, or any package it builds, holds any string from the private-markers file (`--private-markers`; `publish.sh` reads `~/.config/ibara-release/private-markers`): one string per line that must never be published, such as the maintainer's own addresses, host names and account names, compared without regard to case, in file contents and file names. The list stays outside every repository, because committing it would publish it. Core's development history holds such strings, so it is published from a local `public` branch instead: an orphan branch whose commits are snapshots of `main`'s tree, each with the previous snapshot as its parent (`git commit-tree main^{tree} -p public -m …`, then `git branch -f public <commit>`), pushed as the GitHub repository's `main`, its default branch; releases are cut from a checkout of `public`. Every installed computer trusts only the key built into its `ibara`: without the private key no computer can be updated again, and moving to a new key takes one last release signed with the old key whose `release.env` names the new one, so keep an offline copy of `~/.config/ibara-release/`. Without `--publish` the release is a draft; `gh release edit vVERSION -R MayberryDT/ibara --draft=false --latest` publishes it. A release published while someone is downloading can fail that one download (a package missing, or a manifest and signature from two releases, which fails the signature check); nothing is installed, and trying again gets the new release.

`src/install/` is what the package cannot do by itself:

Starting without the disk password (`unattended_boot.rs`) changes only a computer laid out as Omarchy lays it out, and refuses anything else with one sentence: a LUKS2 root opened by the busybox `encrypt` hook from `cryptdevice=DEVICE:NAME` on the kernel line (`/etc/default/limine`, and `/etc/kernel/cmdline` when it has it too), a TPM 2.0 Linux can use, Omarchy's `omarchy_hooks.conf`, and Limine booting UKIs that `limine-mkinitcpio` builds (`ENABLE_UKI=yes`). `enable` backs up the LUKS header, `/etc/default/limine`, `/etc/kernel/cmdline` and `limine.conf` to `/var/backups/ibara/unattended-boot/<time>/`; writes `/etc/ibara/unattended-boot.json` (what changes, so `disable` can put back even an interrupted run); adds a boot entry `ask-disk-password` on a copy of the running UKI with the kernel line it had (`/etc/limine-entry-tool.d/zz-ibara-ask-disk-password.conf`); writes `/etc/mkinitcpio.conf.d/zz-ibara-unattended-boot.conf` (after Omarchy's drop-ins: `udev`→`systemd`, `keymap consolefont`→`sd-vconsole`, `encrypt`→`sd-encrypt`, `btrfs-overlayfs`→`sd-btrfs-overlayfs`, `resume` dropped because the systemd hook resumes itself; `plymouth` and the rest stay); replaces the `cryptdevice=` word with `rd.luks.name=UUID=NAME rd.luks.options=UUID=tpm2-device=auto[,discard]`; runs `limine-mkinitcpio` and checks every kernel entry and image (it goes on past a failed kernel, so its exit status says too little); then enrolls a TPM2 key beside the password (`systemd-cryptenroll`, which asks for the disk password) sealed to PCR 7 as the new initramfs will find it. systemd's initramfs extends PCR 7 with SHA-256(`os-separator`) (`systemd-pcrosseparator.service`, on a measured UKI boot) before it opens the disk and the busybox one never does, so a key sealed to PCR 7 as it reads during the Omarchy boot never opens: enable passes `--tpm2-pcrs=7:sha256=<predicted>`. When the prediction equals PCR 7 now, `cryptsetup open --test-passphrase --token-only` proves the key. A failed step puts back everything before it. `ibara-unattended-boot.service` (`boot-check`) removes `ask-disk-password` after the first start whose journal shows systemd-cryptsetup unlocking with the TPM. `disable` puts the files back, rebuilds, removes the entry and wipes the TPM key; the password slot is never touched. The power helper's `disk` asks `unattended_boot::status()` once ibara has turned this on, so the restart warning is right before the first restart and again whenever `/etc/default/limine` or the drop-in changed since (the next start may ask). Proof: a qemu VM with swtpm laid out as Omarchy.

What it gives up, said in the Settings help and `status`: the TPM key is sealed to PCR 7, the Secure Boot state, which does not cover the kernel line. With sbctl and snapper, as Omarchy sets them up, `limine-mkinitcpio` builds the images without an embedded `.cmdline`, Omarchy does not enroll the Limine configuration (`ENABLE_ENROLL_LIMINE_CONFIG`), and Limine's editor is on, so anyone at the keyboard, or with the unencrypted ESP, can add `init=/bin/bash` to the kernel line; systemd-stub then measures that line into PCR 12, which the key is not bound to, and the TPM still opens the disk. So ibara never says Secure Boot protects the disk: anyone who has the whole computer can get at the files, and only a disk taken out of it stays unreadable. Binding PCR 12 as well would need every image to carry its own `.cmdline` (or an enrolled Limine configuration with Secure Boot on) and a predicted PCR 12; ibara does neither.

Omarchy signs the desktop account in without a password once the disk is unlocked (SDDM's `[Autologin] User=`, read as SDDM reads it: `/usr/lib/sddm/sddm.conf.d/*.conf`, `/etc/sddm.conf.d/*.conf`, then `/etc/sddm.conf`, the last `User=` winning), and nothing locks the screen at session start. With that on, `enable` (the person's command before `sudo`, and `check()` as root) refuses until the lock at sign-in is on, `status` and the console say so, and `lock-at-sign-in off` is refused while it is all that keeps the desktop closed. `lock-at-sign-in on` writes `~/.config/omarchy/hooks/post-boot.d/00-ibara-lock-at-sign-in` (Omarchy's hook folder; `omarchy-hook post-boot` runs it about two seconds after Hyprland starts, at every sign-in), which asks `omarchy-shell lock lock` every half second until the shell answers `ok`, for up to 30 seconds; `off` removes the file. It counts as on only while the file is exactly what ibara writes. Limits: the desktop is open for those first seconds, and a shell that never starts leaves it unlocked (the hook then fails, and `omarchy-hook` logs it).

`/opt/agent-computer/current` points at `/usr/lib/ibara`, so every path earlier releases wrote (sshd forced commands, `/usr/local/sbin/ibara-op-shell`, browser native hosts) keeps working; a computer that ran a release tree keeps it as `previous`. Setup is idempotent: each step names itself when it fails and nothing after it runs. `policy.json` is written once and then left to the person, except that the file limit earlier releases wrote (`max_artifact_bytes` 268435456, 256 MiB) becomes 250,000,000; any other value stays. It restarts the agent entry and the root helpers only when a file they run from changed (a digest in `/opt/agent-computer/*.sha256`), and the agent entry's `KillMode=process` keeps agents' sessions through a restart.

A computer set up by hand before the package (release trees, a console in `~/.local/share/ibara-client`) moves over with the same install: setup replaces `~/.local/bin/ibara` and `ibarad` when they are copies or links into that tree (other old links, such as `ibara-mcp`, stay), sets aside the unit files under `/etc/systemd` and `~/.config/systemd/user` that would hide the package's, and then restarts the agent entry and root helpers from the package's units whatever the digests say. The installer runs `/usr/bin/ibara setup`, never an older `ibara` earlier in `PATH`. Hand-installed `/usr/bin/ibara-stream`, `/usr/bin/ibara-view` and `/usr/share/ibara-stream` must be moved away first, because pacman refuses files it does not own.

`packaging/e2e/` proves it end to end in a throwaway nspawn container (`container.sh`, then `scenario.sh EVIDENCE RELEASE_1 RELEASE_2 PLUGIN`; `container.sh channel` serves a release built for the GitHub address as GitHub does, through `release-server`: the Latest redirect, then the asset host, over HTTPS with a CA only the container trusts): tampered releases refused, the one-line install, setup again, a Hyprland upgrade, update with What's New, rollback with later revocations kept, uninstall, the marketplace route, and `stream-check`, which starts the packaged `ibara-stream` as `LiveStream` does and `ibara-view` with a console's bundle on a headless sway desktop, and passes only when the viewer is admitted, receives video, and revoke settles. The packaged builds keep Arch's `-D_GLIBCXX_ASSERTIONS`, so this also catches out-of-range container access a developer build lets through.

Updates: `stable.json` (schema 2: `packages` names `ibara`, `ibara-stream` and `ibara-view` at the release's version, each with SHA-256 and size) and `stable.json.sig` at the release address, the SSH signature (`ssh-keygen -Y sign -n ibara-release`) checked against the built-in key, each package checked against the manifest, then one `pacman -U` of all three as root. Each installed release stays in `/var/cache/ibara/packages` (three releases kept); the journals are copied by the desktop account to `~/.local/state/ibara/backups/before-VERSION-…` first. `ibara rollback` installs every kept package of the newest release older than the installed one and, when the newer version had moved the journal to a newer core schema, puts back that copy (the newer journal is kept beside it), keeping pairings ended and permissions removed or narrowed since the update as they are now. After an update `~/.local/state/ibara/whats-new.json` holds the release notes; the console shows them once.

## End-to-end harness

`src/harness/` is `ibara harness`: runs of contract 4 through any MCP server command, the "end-to-end first" tests. The server command follows `--`: `ibara mcp --directory-db FILE --computer NAME` on an operator, or `tailscale ssh …` into `ibara agent-entry` with `SSH_ORIGINAL_COMMAND=mcp` on a target.

| Mode | What it does | Passes when |
|---|---|---|
| `probe` | `initialize`, `tools/list`, `computer_status`, `computer_status({ref: "help:computer_act"})` | every call answers `ok` |
| `dogfood` | The standard task: begin with a `file_content` check on `dogfood.txt`; launch the editor expecting its window (the frame's launch choice when offered); type `dogfood <UTC date>` through the frame's typing choice, expecting the text; in one act, `ctrl+s` expecting the Save As dialog, type the begin result's `workspace` path, `Return` expecting the dialog gone, then expect the file; publish; read the file back; finish `complete` | the finish is `complete` with every check met and the file reads back as the line |
| `approval` | Writes `approval.txt`, sends it (held, `pending` with an `att_` reference), repeats it (still held), runs `--approve-cmd` with `{att}` replaced, waits for the answer, repeats the send (runs), repeats it again (the same result) and counts the artifacts | the send runs once after the answer |

Choices come from the returned frames; no element id is written in. A floating Save As already listed when the task begins, usually left by an earlier run, stops `dogfood` before the launch. A launch that leaves a dialog in front stops the run instead of typing into it. Every run writes a JSON report (`--report FILE`, else stdout): each request's tool, milliseconds, request, response and image bytes, status and error code; totals; the outcome; and the full transcript without image data. It exits 1 when the run did not pass.

The target returns freed capture/PNG allocator pages to the OS when no task holds control (glibc builds). This preserves live records and keeps memory after real use within the idle gate; measure after console/capture work as well as after startup.
